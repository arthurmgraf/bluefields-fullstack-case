## Summary

AgentSpec 5.0 is a major evolution of the SDD (Spec-Driven Development) workflow and Dev Loop, upgrading from AgentSpec 4.2 (avg score 6.4/10) to a parallel-first system targeting 9.0/10. The upgrade delivers real parallelism in both `/design` (background research subagents) and `/build` (git worktree isolation per work group), a mandatory Plan Mode quality gate before any subagent implements code, automatic code review post-build via `code-reviewer` with persistent memory, a real-time DASHBOARD per work group, a HISTORY artifact index on every /ship, contextual guidance at the end of every phase, Docker AFK sandbox for unsupervised runs, incremental verification cache, and Dev Loop v2.0 with `team_size` parallel batch execution. All 23 files (17 modified, 6 created) across 5 work groups were delivered in a single sprint on 2026-02-25, updating workflow contracts, 8 agent definitions, 7 command files, 5 templates, and the main CLAUDE.md.

## Lessons Learned

### Process

What worked well and what to improve in the SDD process:

- The BRAINSTORM → DEFINE pipeline proved highly effective: the 7-question dialogue in BRAINSTORM captured all requirements that made DEFINE precise (14/15 Clarity Score)
- Splitting the 23 files into 5 work groups in DESIGN was essential for cognitive organization, even though the build ran sequentially (bootstrapping paradox)
- Context continuation mid-session (Work Group B → Work Group D) worked cleanly with a summary handoff — no data loss
- The bootstrapping paradox (building parallel execution features sequentially) is unavoidable in v1 — future builds of AgentSpec will benefit from the very parallelism they implement

### Technical

Technical insights gained during implementation:

- YAML frontmatter is a prerequisite for all v5.0 agent features (`memory: project`, `isolation: worktree`, `hooks`, `background: true`). Without frontmatter migration on all 40 agents that lacked it, the parallel and memory features will not activate
- The Plan Mode loop (plan → leader review → approve/reject → implement) is architecturally clean but adds a round-trip per work group. The built-in circuit breaker (3 rejections → leader takes over) prevents infinite loops
- team_size auto-recommendation thresholds (0/<4, 2/4-6, 3/7+) are heuristics that will need calibration based on real execution data
- The Docker AFK sandbox and worktree isolation are independent mechanisms: Docker protects the host filesystem; worktrees protect between subagents. Both are needed for truly safe parallel AFK execution

### Communication

Clarifications that prevented rework or could have prevented confusion:

- Early clarification in BRAINSTORM that Agent Teams is out of scope (experimental, Windows incompatibility) prevented an entire design path that would have been thrown away
- The YAGNI check in BRAINSTORM (memory? hooks? team_size?) was explicit and user-confirmed — none of the 3 extras needed post-design rework
- The "bootstrapping paradox" deviation in the BUILD_REPORT was transparent and documented, preventing confusion about why a parallel-build feature was built sequentially

### Tools and Libraries

Tools that proved valuable in this implementation:

- YAML frontmatter as the canonical format for Claude Code agent configuration — enables memory, hooks, isolation, and background execution as first-class features
- `git diff --name-only` as an incremental verification cache — simple, accurate, no custom tooling required
- The Task tool with `run_in_background: true` as the mechanism for parallel subagent spawning — no additional infrastructure needed beyond standard Claude Code
